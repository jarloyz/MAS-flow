# MAS-Flow Tools and Stack

Since MAS-Flow is a conceptual and methodological framework, it is agnostic to the underlying technology. However, to implement it correctly, certain infrastructure is required.

## 🧠 Recommended Large Language Models (LLMs)
Match model capacity to the cognitive load of each role:

| Tier | Roles | Example (Claude) |
| --- | --- | --- |
| Highest reasoning (one run per story) | Planner, Architect, Security, Guard `plan_review`, Fixer | Fable / Opus |
| Balanced coding/auditing | Executors, Guard, Documenter | Sonnet |
| Fast & cheap | Researcher, Tester | Haiku |
| No model | git, slice checks, verify, logging, archiving | `masflow.py` |

The Orchestrator only routes, so a balanced model is usually enough.

## ⚙️ Agentic Orchestration Frameworks

### Ready-made runtimes (reference implementations)
Generated by `scripts/masflow.py sync` from the same portable prompts:
- **Claude Code:** subagents with per-role tool restrictions and models, a `/masflow` orchestrator skill, and hooks to enforce environment rules. See [Running MAS-Flow with Claude Code](claude_code.md).
- **OpenCode:** `.opencode/agents/` with per-role tool switches (models stay in `opencode.json`).

### Build your own
To build the Orchestrator and the agents' cycles, you can use:
- **LangGraph / LangChain:** Ideal for cyclical flows (Feedback loops) and persistent state control.
- **CrewAI:** Excellent for declaratively defining roles and delegating tasks (though you'll have to force the asynchronous/Kanban model).
- **Microsoft AutoGen:** Very powerful for direct conversation between the *Tester*, the *Executor*, and the *Guard*.
- **Custom Scripts (Python/Node):** Often, building your own pipeline that reads and writes to `.masflow/handoff.md` is the cleanest way to implement MAS-Flow.

Whatever you choose, reuse `scripts/masflow.py` for the steps that need no model (`git`, `checks`, `verify`, `log`, `archive-story`, `check`, `stats`): they print a result envelope as JSON and work the same from any orchestrator.

## 📂 State Files (External Memory)
The implementation must have read/write access to the disk (Workspace) to read/modify code and update:
1. `handoff.md` and `slices/`: the state of the current story and one spec per slice.
2. `core_architecture.md`: the single source of truth for the project's tech stack and design patterns.
3. The maps, `board.md`, `lessons.md`, `history.md` and the machine records (`events.jsonl`, `baseline.json`, `verify_log.md`). See the [Protocol](protocol.md).

## 🛡️ Auditing Tools (For the "Guard" and "Tester")
To avoid relying 100% on the LLM, the Guard and Tester can use deterministic tools under the hood:

- **Linters & Static Analyzers:** Configure tools like PHPStan, ESLint or a formatter in check mode as `slice_checks`: `masflow.py checks` runs them on every slice, before any model reads the code.
- **Test Runners:** The *Tester* runs the related tests and acceptance commands at story close; `masflow.py verify` runs the full suites daily. A JUnit report (`tests.junit`) makes the comparison with the baseline exact.
- **Graduating rules:** when the same finding repeats, prefer a new deterministic check (lint rule, architecture test) over a new prompt rule.

## 🔌 Model Context Protocol (MCP)
To truly empower your agents, MAS-Flow highly recommends utilizing the **Model Context Protocol (MCP)**. MCP allows your AI agents to securely connect to local tools and data sources.

- **Database Access:** Use MCP to let the *Tester* query a local testing database to verify if an action (like creating a user) actually worked.
- **Documentation:** Use MCP servers for framework and platform docs so executors do not guess APIs.

Equipping agents with MCPs transforms them from passive text generators into active system operators.
